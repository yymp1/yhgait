# 步态检索 GUI 的边界与下一步

## 当前这个 GUI 到底是什么

它是一个：

- 基于 `CASIA-B` 数据集
- 基于真实 checkpoint
- 基于真实 embedding 检索结果
- 用来展示 Top-K 检索效果与案例差异的分析页面

它不是一个：

- 真实业务视频系统
- 端到端视频识别产品
- 可以直接拿去证明线上真实场景效果的 demo

## 为什么它和真实业务系统不是一回事

当前页面默认的输入其实已经是“整理好的 gait 序列”。

也就是说，它跳过了真实业务中最麻烦的前半段：

1. 原始视频读取
2. 人体检测
3. 多目标跟踪
4. silhouette / 前景提取
5. 稳定 gait 周期切分
6. 序列质量控制

而这些环节，往往正是现实效果会明显下滑的地方。

## 这轮 demo 真正证明了什么

1. 当前 checkpoint 能在受控数据集上给出真实、可见的检索效果
2. `00500 -> 01000` 的改进不只是训练日志上的变化，在样例层也能看出来
3. 现在已经有一个可展示成功和失败的闭环页面，可以用于内部判断模型状态

## 这轮 demo 不能证明什么

1. 不能证明真实视频场景已经可用
2. 不能证明摄像头输入下会有同样的命中率
3. 不能证明复杂遮挡、多目标和低质量分割下仍然稳定

## 如果要继续往真实视频 demo 走，下一步最应该做什么

主建议只有一个：

- 先打通 `真实视频 -> 单人轨迹 -> silhouette 序列 -> 当前 embedding + retrieval` 的最小链路

原因：

- 当前训练和检索页面已经够用来观察“模型本身在数据集上的效果”
- 继续往前推进，最有价值的不是再堆训练长度，而是补齐真实视频前处理链路
- 只有把那条链打通，我们才能知道“业务落地风险”到底主要在模型，还是主要在前处理
